A workspace template for AI agent teams

Artifact Driven

Write the knowledge first and agree on it. Then build the code that proves it. Every rule, scenario and contract has an ID, every page cites only the layer below it, and a script can tell you what a change will touch before you make it.

The whole team builds it, and each person owns their part: a service, a client, the knowledge. People and AI agents do the work; the owner of each part approves its share. It holds for one backend or many services.

Knowledge

Four layers, and every citation points down

The system is shared by everything. Below it, a goal cites flows and a flow cites artifacts. An artifact never mentions a flow or a goal, so a change can be traced in both directions.

LayerHoldsIDProved by
SystemPurpose, actors, services, clients, system-wide requirements, glossary, shared contract partsSYS-4Everything below it
GoalA business outcome: the need, the actor and the success criteria. No behavior.G-BORROW-2End-to-end tests
FlowBehavior across artifacts: trigger, steps, the transaction, failures. Scenarios as given, when, then, each naming an operation or a trigger.F-BORROW-3Command and unit of work tests
ArtifactOne domain: model, rules, lifecycle, the OpenAPI contract, and what each client needs from its responsesBK-5Domain unit tests

One owner per fact

Other pages cite the ID and never restate the rule. A contract description cites the rule behind a value.

Knowledge, not evidence

No code locations, logs, counts or dates in the knowledge. Evidence goes on the issue, with personal data masked.

IDs live forever

An ID is fixed when its branch merges. A dropped fact keeps its row as Withdrawn. and nothing cites it again.

Contracts first

OpenAPI is agreed before the code: endpoints, payloads such as emails and pushes, and worker triggers under x-triggers.

Clients say what they need

Each client page lists, by operation, the keys and values a released app parses, so a change to a service cannot break it unseen.

Open questions name IDs

Undecided behavior is written as a question citing the IDs it touches. A goal with open questions is not ready to build.

Definition of done

Seven items, all visible on the issue

Why this one

Beside BMAD and Spec Kit

All three put a written spec in front of the AI agent. They differ in what the spec is for. BMAD and Spec Kit write documents that lead to the next feature. Artifact Driven keeps one body of knowledge for the whole system and checks it with scripts, so you know what a change breaks before anyone writes code.

Choose Artifact Driven when

The system lives for years and most work changes rules that already exist. One backend or many services serve several clients, and each must know what a change does to its responses. You want a script, not a model, to say that a rule is cited, covered and tested.

Choose BMAD when

You start from an idea and need the discovery: brainstorming, research, a PRD, an architecture and stories, from agents that work like an agile team.

Choose Spec Kit when

You want to go from a feature description to a spec, a plan and tasks in minutes, in one repository, with the coding agent you already use.

They are not exclusive. A PRD from BMAD or a spec from Spec Kit is a good source for the first goal here.

Tools

Python scripts that read the citations

Standard library only. They read artifact-driven.json for the knowledge folder, the clients, and the routes and tests of each service.

Check the docs

Broken links and anchors, IDs cited but not defined, defined twice or withdrawn, and scenarios with no operation.

python3 scripts/check_docs.py

Impact

What a rule, operation or response field affects, or what a goal relies on, by following the citations.

python3 scripts/impact.py MBR-2
python3 scripts/impact.py --down G-BORROW-1

Size, fragility, coverage

Goal size and blast radius, the most fragile nodes, test coverage by ID and the open questions that hold each goal.

python3 scripts/impact.py --stats
python3 scripts/impact.py --questions

Tests name real IDs

Reports a test, in any service or client, that names an ID the knowledge does not define, or a withdrawn one.

python3 scripts/check_tests.py

Knowledge site

One offline HTML page in English or Vietnamese: pick goals, see their scenarios, gaps, blast radius and API coverage.

python3 scripts/site.py

Structure

Every directory has a README, so the repository reads like a book.

python3 scripts/check_structure.py
Start a project

Install the workspace, add your repositories, write the first goal

  1. Create the workspace

    The installer copies the rules, the scripts and the library sample into a new folder. Then start its repository and rename the README and the site title.

    curl -fsSL https://raw.githubusercontent.com/hieutran21198/Artifact-Driven-Framework/main/install.sh | sh -s -- my-workspace
cd my-workspace
git init

  2. Clone the services and the clients

    One or many of each, with the owner of each. List them in artifact-driven.json with the same names as their folders, so each artifact gets a <client>.md page and each service its routes and tests.

    git clone <service repository URL> services/<service>
git clone -b <branch> <client repository URL> apps/<client>

  3. Describe the system

    Context, actors, services and clients, system requirements, glossary, supported client versions and the shared contract parts. Fill in the domain map, the infrastructure pages and the deploy table.

  4. Write the first goal

    Follow the runbooks: the goal, its flows, the artifacts they cross, their contracts and client pages. Run the checks after each step.

  5. Remove the reference pass

    When the first real goal exists, delete the library example and point the runbook samples at your own pages.

  6. Work by the workflow

    Every change starts as an issue. People and agents write, review and implement; the owner of each part approves its share.
