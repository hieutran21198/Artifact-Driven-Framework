Artifact Driven

A workspace and workflow for teams to agree software behavior, then build code and tests from it.

02

Knowledge

Each fact has one owner and an ID. Other pages cite that ID instead of copying the rule. The links let the scripts trace what a change affects and what a goal relies on.

Goal · Borrow a book
G-BORROW-1: a member in good standing borrows an available book and sees when it is due.
Flow · Borrowing
borrowBook checks the member and book, records the loan in one transaction, and returns the book with its due time. A refused loan changes nothing.
Artifacts · Book and Member
BK-3 permits lending only an available book. MBR-2 sets the member's regional loan limit; MBR-3 and MBR-4 block borrowing for suspended members or members with an overdue book.

The OpenAPI contract defines the operation and response. Each client page records what that client needs from them. Contracts, client needs and tests connect to the four layers; they are not extra layers.

Source: Knowledge rules. For a new need, start with shape a need, then write the goal and flow.

03

A change

Change the default loan period from 14 to 21 days, for new loans only.

The sample's BK-4 records the borrower and a due time loan_days after the loan. The setting defaults to 14; a change applies to new loans only. This example changes the default to 21 and keeps existing due times.

  1. Confirm the scope and trace the impact

    The coordinator clarifies the need with the person who raised it, then runs python3 scripts/impact.py BK-4. Read the linked flows, contracts and client needs before choosing which parts to change. If the choice is still open, compare the options and the rules each keeps, changes or adds, then ask the owner about the chosen option before writing knowledge.

    The requester confirms the 21-day default and unchanged existing due times. Guidance: clarify the need and trace the rule.

  2. Update the knowledge and dependencies

    A solution architect or knowledge-writer agent changes the default in BK-4. The contract designer checks the contract; if its promises still hold, no contract edit is needed. Client writers check each affected client's needs.

    The mobile app's help text states the default loan period, so it needs an update. For the period, the web client uses the returned due_at; it also reads other fields. Check that dependency rather than assuming the web needs no work.

    Owners check the rule and each client's recorded needs. Runbooks: change a rule, check the contract, check client needs.

  3. Review and approve the knowledge

    An independent reviewer checks the affected pages and reports findings. The product owner approves goal changes; each affected service or client owner approves their share. The owners merge the knowledge branch. The code work uses that approved knowledge.

    Owners check the review findings and resolve questions that block approval. Follow the check runbook and knowledge approval.

  4. Implement and test each affected part

    In a project with service and client code, developers or implementer agents change the lending default and mobile help text. Tests name the IDs they prove. Test the new default and confirm that existing loans keep their due times.

    Owners check those test results, including failures and skipped tests. Guidance: implementation workflow and test ID checks.

  5. Review the code and prepare requested pull requests

    A reviewer who did not write the change checks the code against the knowledge and runs the relevant tests. The coordinator commits, pushes and opens pull requests only when asked. Each pull request links the issue and knowledge merge commit; owners approve their parts before a requested merge.

    Owners check the review, test evidence and both links before approval. Use the check runbook and Done.

Roles can be people or agents. Use only the roles the change needs. Follow the workflow for exceptions and the definition of done for release requirements.

04

Checks

The framework reads knowledge and tests as text. Its static checks do not run the product or prove that the code follows the rules.

Docs consistency
python3 scripts/check_docs.py
Finds broken Markdown links, missing or invalid IDs, invalid citation direction, and scenarios or operations with missing links. check_structure.py checks README coverage.
Recorded impact
python3 scripts/impact.py BK-4
Follows recorded links to affected knowledge, contracts and clients. A dependency missing from the knowledge will not appear.
Test ID presence
python3 scripts/impact.py --coverage
Reports which knowledge IDs appear in test files. check_tests.py finds cited IDs that are unknown or withdrawn. Neither command proves that a test passes.
Runtime tests
Run the tests of each changed service and client. Domain tests prove artifact rules; command tests prove flow scenarios; end-to-end tests prove goal criteria. Record the actual results and gaps on the issue or pull request.

Open the project tracker to explore a workspace's knowledge and test ID coverage at a selected revision. It remains separate from this guide.

05

Start

Install into a new folder with POSIX sh, curl and tar. The checks need Git and Python 3.9 or later.

curl -fsSL https://raw.githubusercontent.com/hieutran21198/Artifact-Driven-Framework/main/install.sh \
  | sh -s -- my-workspace

This command downloads and runs the install script. To inspect it first or choose a fixed version, use the download-first instructions.

Open the workspace, initialize Git, and check the sample:

cd my-workspace
git init
python3 scripts/check_structure.py
python3 scripts/check_docs.py
python3 scripts/impact.py BK-4
python3 scripts/site.py

Open build/site/index.html to explore the sample. It is documentation for a lending system, not a running library app. No lending service or client implementation is included.

To try the same change with your coding agent, open it in the workspace and give it this task:

Change the default of loan_days from 14 to 21 days, for new loans only. Work as the team in AGENTS.md. Confirm the scope before editing, trace BK-4, update the sample knowledge, and report the checks and remaining gaps. Do not invent missing service or client code. Do not commit, push or open pull requests.

Check the agent's work

  • Confirm it clarifies the need before writing.
  • Check that knowledge comes first and any implementation waits for the owners' approval.
  • Inspect the actual impact output and applicable check results, including failures, skipped checks and missing code.
  • Review the remaining gaps. Keep commits, pushes, pull requests and merges within the team's approval limits.

For your own project, follow Start a new project: clone your parts, describe the system, and replace the sample after your first goal, flow and artifact exist.

Agent roles and tools

The main session coordinates the work. .agents/agents defines the knowledge writer, contract designer, client writer, implementer, defect investigator and reviewer. Their scope comes from the team rules; current tool and model settings are in the agent definitions.

Claude Code
CLAUDE.md imports AGENTS.md. The links in .claude expose the roles and skills. Ask for the relevant agent by name. Vendor docs: project instructions, subagents and skills.
Codex
Use AGENTS.md for project instructions and .agents/skills for skills. When delegating, point the subagent at its role file and state its write limits. Vendor docs: project instructions, skills and subagents.
Terms
Knowledge
Agreed statements of what the product must do. Evidence, plans and status stay on issues or pull requests.
Goal, flow and artifact
A user story describes a goal's need; acceptance criteria map to its success criteria. A use case maps to a flow. A bounded context describes the domain an artifact owns, without requiring a module boundary inside a service.
Part and owner
A part is a service, client or shared knowledge with an owner. The owner approves changes to that part.
Test ID coverage
The share of knowledge IDs found in test files, not a measure of code correctness or a record of passing tests.

Approval and work limits

A role changes only its assigned parts. Each handoff gives the coordinator the changes, IDs, check results and open questions. A knowledge gap found during implementation goes back to the knowledge writer.

The reviewer and defect investigator change no files. Owners merge knowledge branches. The coordinator commits, pushes, opens pull requests, merges code, deploys or releases only when the relevant owner asks. An issue being closed is not approval.
