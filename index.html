Artifact Driven

A simple way to keep software development clear for years, with fast analysis and a quick view of what every change affects. No cost, no overhead.

The structure

  1. GoalWhat someone needs.A member borrows a book.
  2. FlowHow it happens, step by step.Borrowing, returning.
  3. RuleWhat must stay true.Only a book on the shelf can be lent.
  4. ArtifactOne topic and its rules.Books, members, notices.
  5. AppWhere people do it.Website, phone app.

Example: borrowing a book

A library lends books to its members. A member picks a book from the shelf and takes it home. They bring it back within 14 days, and the book goes back on the shelf. If it is late, the library sends them a note.

How to break down a requirement

A member wants to read books at home. They borrow up to a few books, only those on the shelf, for 14 days. They bring them back, and a late book is flagged.

  1. Write the goal

    Who needs what, and how you will know it is done.

    A member can borrow a book and sees when it is due.

    Goal · Borrow a book
    • A member borrows an available book and sees when it is due.
    • A book is on loan to one member at a time.
    • A member never holds more books than the limit.

  2. Split it into flows Specs by example

    Write the steps of each flow as scenarios: what happens, and what happens when something goes wrong.

    The book is already on loan, so the request is refused.

    Flow · Borrowing

  3. Pull out the rules

    Read each step and write down what must always be true. Words such as "must", "only" or "at most" are good hints. A person does this by reading; no tool guesses rules from words.

    Only a book on the shelf can be lent.

    Read a step, write the rule (by hand)
    borrow only from the shelf→On the shelf only
    at most a few books→A few books at most
    must be back in 14 days→Due in 14 days

  4. Group the rules by topic Strategic DDD

    Each topic is an artifact: one domain.

    Books, members, notices.

    Artifacts
    BooksOn the shelf onlyDue in 14 daysLate is flagged
    MembersA few books at most
    NoticesOne reader each

  5. Note what each app needs Contract first

    The API calls and fields each app relies on, so a change does not break it.

    The phone app reads the due date of a book.

    Contract · what the phone app reads
    POST /v1/books/{id}/borrow

{
  "id": 1,
  "title": "A Field Guide to Birds",
  "status": "on_loan",
  "due_at": "2030-01-15T18:00:00Z"
}

  6. Mention the rule in its test

    Each rule has a short ID. The test that checks it mentions the ID, so the scan can find it.

    BK-3 is the rule "only a book on the shelf can be lent".

    Test and scan
    // BK-3: only a book on the shelf
func TestLendBookOnLoan(t *testing.T) {
  err := onLoanBook().Lend(member)
  assert.Error(t, err)
}

Good to know

Scan

The scan shows which rules are in the product. It does not show that they work.

How it works: it reads the test files and looks for rule IDs, such as BK-3. It does not run the tests or read the product's code.

Impact

Find every part a change affects, in seconds.

How it works: it follows the links from a rule up to its flows and goal, and across to the apps that use it. It does not estimate cost or time.
