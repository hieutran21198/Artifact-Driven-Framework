Framework

Files of a workspace

my-workspace/
├── README.md
├── CONTRIBUTING.md               how to make and check a change
├── AGENTS.md                     instructions for coding agents
├── CLAUDE.md                     imports AGENTS.md
├── artifact-driven.json          configuration the scripts read
├── .agents/
│   ├── agents/                   one agent per role
│   └── skills/                   software-knowledge, defect-triage, backend-service, plain-writing
├── .claude/                      links to .agents
├── docs/
│   ├── architecture/
│   │   ├── decisions.md          why the method is shaped this way
│   │   └── domain-map.md         each domain and the service that serves it
│   ├── governances/
│   │   └── artifact-driven/
│   ├── coding-standards/
│   ├── infrastructure/
│   ├── principles/
│   └── software-knowledges/
│       ├── system/               context, requirements, glossary, openapi.yaml
│       ├── goals/                <goal>.md
│       ├── flows/                <flow>.md, <flow>.openapi.yaml
│       └── artifacts/
│           └── <artifact>/       README.md, specification.md, openapi.yaml,
│                                 service.md, <client>.md
├── scripts/
├── services/                     one clone per service
├── apps/                         one clone per app
└── e2e/                          end-to-end tests

Parts

  • Governance: what the team writes, and who approves it.
    • Knowledge: what each page holds, and how pages cite each other.
    • Workflow: the steps from an issue to merged knowledge and code.
    • Team: the parts, their owners, and the roles that do each step.
    • Done: what a change needs before it counts as done.
    • Decisions: the reason for each governance choice, and what it costs.
  • Runbooks: the steps for each kind of change.
    • Shape a need into a goal.
    • Add or change a goal, a flow, an artifact rule or a contract.
    • Describe what an app reads, start an artifact, move or split knowledge, remove an API call.
    • Handle a reported defect, fix stored data, report a release, check the docs.
  • Scripts: the checks to run before a review, and the impact of a change.
    • check_structure: a README in each folder.
    • check_docs: broken links, unknown IDs, a rule citing a flow, a scenario with no API call.
    • check_tests: tests name only IDs the knowledge holds.
    • impact: what a change to a rule reaches.
    • site: one HTML page that shows how goals, flows and artifacts link.
  • Install script: one command that creates a workspace with these parts.
    • install.sh <folder> [ref], from any branch, tag or commit of the framework.
    • The workspace starts with the library sample.
