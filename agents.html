Work with coding agents

A workspace tells a coding agent how the team works: who does each step, with which skill, and what each one may change. This page shows what is in the workspace, how Claude Code and Codex use it, and one change of the sample library from the issue to the pull request.

What a workspace gives an agent

Every new workspace has these files. The copies in .agents are the ones to change; .claude only links to them.

AGENTS.md      instructions
CLAUDE.md      @AGENTS.md
.agents/
  agents/      one per role
  skills/
    software-knowledge/SKILL.md
    defect-triage/SKILL.md
    backend-service/SKILL.md
.claude/
  agents -> ../.agents/agents
  skills -> ../.agents/skills

Each agent file also lists its tools: the investigator and the reviewer have no Edit or Write. The main session is the coordinator and has no file. The roles are on the team page.

How each tool uses it

Claude Code

Reads
CLAUDE.md, which imports AGENTS.md. Docs
Finds
The agents in .claude/agents and the skills in .claude/skills, through the links. Subagents · Skills
Hands a step
Name the agent in the prompt. It runs with the tools and the model of its file, and reports back to the main session.

Codex

Reads
AGENTS.md, from the repository root down to the folder it starts in. It does not read CLAUDE.md. Docs
Finds
The skills in .agents/skills. Type $ or /skills to name one. Skills
Hands a step
The agent files are written for Claude Code; Codex keeps its own in .codex/agents, and a workspace has none. Ask for a subagent and point it at the file of its role. A subagent keeps the sandbox of the session, so the tools line does not limit it: tell a role that writes nothing to change nothing. Subagents

A prompt for each step

1 · IssueRead this issue and the knowledge it links. Which roles does it need, and which can skip?
2 · KnowledgeUse the knowledge-writer agent to write the change. Then one client-writer agent for each app that reads it, in parallel. Then the reviewer agent.
3 · CodeThe knowledge branch is merged. Run one implementer agent for each part it touches, in parallel, then the reviewer agent.
4 · Pull requestsCommit and open a pull request for each part.
5 · CloseCheck Done for this issue and tell me what is missing.

In Codex, write “a subagent that follows .agents/agents/knowledge-writer.md” in place of “the knowledge-writer agent”.

The agents as a team

The order is the one on the team page. Roles on one row run in parallel. A role whose step the change does not need skips it.

  1. IssueCoordinatorDefect investigator, for a defect
  2. KnowledgeKnowledge writer
  3. ContractContract designer
  4. AppsClient writer · webClient writer · mobilein parallel
  5. ReviewReviewer: knowledge
  6. ApproveOwners merge the knowledge branch
  7. CodeImplementer · a serviceImplementer · an appin parallel, one per part
  8. ReviewReviewer: code against knowledge
  9. ApproveOwners approve each pull request
  10. ShipCoordinator: merge, deploy, release, close, when asked
  • The reviewer is never the author of the change it reviews.
  • Each role reports what changed, the IDs, the check results and the open questions. The next role starts from that report, not from memory.
  • A gap found in code goes back to the knowledge writer. No implementer invents behavior.
  • Only the coordinator commits, pushes and opens pull requests, and only when asked. The owners merge.

One session with subagents

Each role does its step and reports back to the coordinator. That is how this flow passes work, so it is enough for most changes, in both tools.

An agent team

Workers that must talk to each other during a step, such as reviewers who challenge each other's findings. In Claude Code, agent teams are experimental and off by default; a teammate can use an agent file of the workspace. Docs
