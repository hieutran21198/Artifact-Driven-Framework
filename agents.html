The work, step by step

At each step the person decides and the agent does the work. Each step follows its runbook; the prompt is one way to start it.

StepThe person decidesThe agent doesThe person checks
1 · Shape the needRunbook

Picks one option, and answers the questions.

Lists what holds today with its impact, lays out the options with the IDs each one keeps, changes or adds, then asks one question at a time.Shape this issue with the shape runbook. Ask me one question at a time.

The IDs listed exist, each option names what it changes, and nothing is written into the knowledge yet.

2 · KnowledgeGoalFlowRule

Which rules hold: the agent proposes them from the steps of a flow, and the person decides.

The knowledge writer writes the goal, the flows and the rules that were settled, and runs the checks.Use the knowledge-writer agent to write what we settled. Propose the rules; add none I have not agreed.

Each new ID names the IDs it was checked against, and the checks pass.

3 · Contract and appsContractClient

The owner of the service approves the contract; the owner of each app, what it reads.

The contract designer, when a shape changes; one client writer for each app that reads it, in parallel.Then the contract-designer agent if a shape changes, and one client-writer agent for each app, in parallel.

The existing response shapes are kept.

4 · ReviewCheck

The owners merge the knowledge branch, or not.

The reviewer runs the checks and reads every page the impact lists.Use the reviewer agent on the knowledge branch.

The findings and the verdict on the issue, and no open item that holds a goal.

5 · CodeWorkflow

The owner of each part approves its code.

One implementer for each part, in parallel, with tests that name the IDs they prove; then the reviewer.The knowledge branch is merged. Run one implementer agent for each part it touches, in parallel, then the reviewer agent.

The tests name the changed IDs, and the test check passes.

6 · Pull requestsDone

When to commit and open the pull requests.

The coordinator commits and opens one pull request for each part, only when asked.Commit and open a pull request for each part. Then tell me what Done still misses.

Each pull request links the issue and the knowledge merge commit.

In Codex, write “a subagent that follows .agents/agents/knowledge-writer.md” in place of “the knowledge-writer agent”.

The agents as a team

Roles on one row run in parallel. A role the change does not need is skipped.

  1. IssueCoordinatorDefect investigator, for a defect
  2. KnowledgeKnowledge writer
  3. ContractContract designer
  4. AppsClient writer · webClient writer · mobilein parallel
  5. ReviewReviewer: knowledge
  6. ApproveOwners merge the knowledge branch
  7. CodeImplementer · a serviceImplementer · an appin parallel, one per part
  8. ReviewReviewer: code against knowledge
  9. ApproveOwners approve each pull request
  10. ShipCoordinator: merge, deploy, release, close, when asked
  • The reviewer is never the author of the change it reviews.
  • Each role reports what changed, the IDs, the check results and the open questions. The next role starts from that report, not from memory.
  • A gap found in code goes back to the knowledge writer. No implementer invents behavior.
  • Only the coordinator commits, pushes and opens pull requests, and only when asked. The owners merge.

One session with subagents

Each role does its step and reports to the coordinator. Enough for most changes, in both tools.

An agent team

Workers that must talk to each other during a step, such as reviewers who challenge each other's findings. In Claude Code, agent teams are experimental and off by default; a teammate can use an agent file of the workspace. Docs

Run it with your own agent

Make the same change in a new workspace, and judge the run by the list below.

  1. Create a workspace with the install command, and open your agent in it.
  2. Give it the issue:Lend books for 21 days by default, not 14. Work as the team of this workspace.

Watch for

  • It asks before it writes, one question at a time. Questions
  • It runs the impact of the rule and names what it reaches. Project instructions
  • It changes the knowledge before the code. Workflow
  • It runs the checks and reports their results. Check the docs
  • It does not commit or push until you ask. Limits
